# NetDisk 渐进式优化设计

- 日期：2026-08-11
- 状态：已由用户确认
- 优化策略：先稳定，再安全，再性能，最后重构

## 1. 背景与约束

NetDisk 由 Qt/Windows 客户端和 Linux 服务端组成。客户端通过自定义 TCP 二进制协议连接服务端，服务端使用 epoll、线程池、MySQL 和 Linux 文件系统完成用户认证、文件管理、上传下载、分享及断点续传。

本设计采用渐进式改造，不整体重写。必须保留现有 MySQL 数据和服务器用户文件；客户端与服务端允许同步升级，不要求长期兼容旧版客户端。

权威源码目录如下：

- 客户端：`D:\Qt -dm\NetDisk`
- Linux 服务端：`D:\Qt -dm\NetDisk\NetDisk_server\NetDisk`
- 根目录下的 `src/`、`include/`：视为旧服务端副本，不参与后续实现

## 2. 已核实的主要问题

- 当前没有有效的 Git 仓库；`.git` 是空目录。
- 根目录和 `NetDisk_server/NetDisk` 存在内容不同的服务端源码副本。
- 构建产物、SQLite 数据库和用户上传文件混在源码树中。
- 服务端数据库账号、密码和文件根目录硬编码在源码中。
- 客户端使用固定盐值 MD5 处理密码，并在调试日志中输出密码与盐组成的原始字符串。
- 已检查的 TCP 传输层没有 TLS。
- 协议直接传输 C/C++ 结构体，依赖编译器布局和平台类型宽度。
- 文件大小及偏移主要使用 32 位 `int`。
- `CKernel` 和 `CLogic` 集中了 UI、网络、数据库、文件和业务状态等多种职责。
- 没有发现自动化测试。

## 3. 目标与非目标

### 3.1 目标

- 原有用户、数据库关系和用户文件保持可用。
- 异常断线、并发请求或进程重启不产生已成功但不完整的文件记录。
- 客户端无法通过伪造用户 ID 访问其他用户资源。
- 密码、数据库凭据和文件内容不以可复用形式暴露在网络、源码或日志中。
- 客户端与服务端共享唯一、跨平台的协议定义。
- 建立可重复构建、自动化测试、性能基线和可回滚的数据迁移流程。
- 在正确性可验证后提高并发传输效率并降低锁竞争。

### 3.2 非目标

- 第一阶段不重写客户端界面。
- 第一阶段不更换 MySQL 或 Qt 技术栈。
- 不在没有基准数据时承诺绝对吞吐量。
- 不在稳定性修复期间同时迁移构建系统。
- 不长期维护 V1 协议兼容层。

## 4. 总体路线

采用六个按顺序执行的阶段。每个阶段必须通过测试、保留回滚能力，并满足本阶段验收标准后才能进入下一阶段。

1. 基线与数据保护
2. 稳定性与数据一致性
3. 安全与配置
4. 协议 V2
5. 性能优化
6. 模块重构与交付完善

## 5. 阶段 0：基线与数据保护

本阶段不改变业务逻辑，只建立后续验证和回滚基础。

### 5.1 数据保护

- 备份 MySQL 数据库，并记录表结构、索引、视图和触发器。
- 备份服务端用户文件目录，生成路径、大小和 MD5 清单。
- 在独立位置建立测试数据库和测试文件根目录。
- 禁止开发和自动化测试直接使用生产数据。

### 5.2 工程基线

- 明确客户端和服务端的唯一构建入口。
- 记录 Qt、编译器、MySQL 客户端库和 Linux 运行环境版本。
- 固化构建、配置、启动和停止命令。
- 将源码、构建产物、配置、日志和用户数据分开管理。

### 5.3 冒烟测试

基线至少覆盖：注册、登录、上传、秒传、下载、文件夹上传下载、新建目录、分享、提取分享、删除、暂停、继续、客户端异常退出、网络中断和服务端重启。上传下载后必须检查文件大小和 MD5。

### 5.4 验收标准

- 现有用户可以登录。
- 现有文件可以列出并下载。
- 新上传文件往返 MD5 一致。
- 数据库和用户文件备份均经过恢复验证。

## 6. 阶段 1：稳定性与数据一致性

### 6.1 网络接收与发送

- 保留现有“4 字节网络序长度 + 数据包”帧格式作为过渡。
- 每个连接维护独立的接收缓冲、解析状态和发送队列。
- epoll 线程不得通过循环读取完整数据包而长时间阻塞。
- 正确处理半包、粘包、`EAGAIN`、超时、断连和非法包长。
- 限制单包大小、连接数、任务队列长度和单连接待发送字节数。
- MySQL 或网络监听初始化失败时，服务端必须启动失败并返回非零状态。

### 6.2 输入与权限校验

- 每种请求先校验精确包长、消息类型、字符串终止符和字段范围。
- 文件名、虚拟目录和本地路径分别校验，拒绝 `..`、绝对路径、控制字符和非法分隔符。
- 登录后由服务端连接状态确定用户身份，不信任请求中的 `userid`。
- 所有文件、目录、分享和删除操作在服务端验证资源归属。

### 6.3 上传状态机

上传依次经历 `created -> receiving -> verifying -> committed`。接收内容先写入临时 `.part` 文件；只有字节数和 MD5 均正确时，才原子重命名为正式文件并提交数据库状态。断线时状态转为 `paused` 或 `failed`，不得被目录查询当作完整文件返回。

### 6.4 下载与续传

- 服务端依据真实文件大小验证续传偏移。
- 偏移和文件大小统一使用 64 位无符号整数。
- 客户端缓存位置只能作为请求建议，最终有效位置由服务端确认。
- 下载完成后客户端重新计算 MD5；不匹配时不得标记成功。

### 6.5 数据库事务

- `t_file`、`t_user_file`、引用计数和文件状态变更使用明确事务边界。
- 上传完成后才将文件标记为可用。
- 删除先解除用户关系，引用计数归零后再删除物理文件和元数据。
- 秒传使用唯一约束、条件更新或事务锁避免并发重复元数据。
- 数据库事务中不得等待网络传输或长时间文件 I/O。

### 6.6 错误模型

统一错误响应至少区分：非法请求、未认证、无权限、资源不存在、冲突、网络失败、数据库失败、磁盘失败、校验失败和服务端繁忙。日志记录请求 ID、用户、资源、结果和耗时，但不得包含密码或密钥。

### 6.7 验收标准

- 断线不会产生可见的不完整文件。
- 并发秒传不会产生重复元数据。
- 删除不会误删仍被其他用户引用的物理文件。
- 大于 2 GiB 的大小和偏移不会溢出。
- 数据库关系、引用计数、文件状态和物理文件一致。

## 7. 阶段 2：安全与配置

### 7.1 配置与权限

- 服务端端口、数据库连接信息和文件根目录移出源码。
- 普通配置放入配置文件；数据库密码通过环境变量或权限受限的密钥文件提供。
- 服务端使用独立的低权限 Linux 用户运行，用户文件目录不再使用 `0777`。
- 数据库使用最小权限专用账号，不使用 `root`。
- 配置缺失、格式错误或目录权限不足时拒绝启动。

### 7.2 TLS

- 全部客户端与服务端流量通过 TLS 保护，最低 TLS 1.2，优先 TLS 1.3。
- 客户端验证服务器证书和主机名。
- 开发和生产使用不同证书，不在生产模式下提供忽略证书错误的选项。

### 7.3 密码迁移

- 新客户端在 TLS 通道内提交密码，不再使用固定盐 MD5 作为网络凭据。
- 新密码在服务端使用 Argon2id；若部署环境无法引入，则使用 bcrypt。
- 数据库记录密码算法和迁移状态。
- 老用户首次成功登录时先按旧算法验证，然后立即写入新哈希。
- 迁移窗口结束并确认无旧账号后，删除旧 MD5 兼容逻辑。
- 日志和错误信息不得记录密码、哈希或数据库凭据。

### 7.4 会话

- 登录成功后将用户身份绑定到连接或高熵随机会话令牌。
- 断线、超时和重新登录时清理旧会话及传输状态。
- 对连续登录失败实施限速和短暂冷却。

### 7.5 验收标准

- 源码和日志中没有真实凭据。
- 网络抓包无法获得可复用凭据或文件内容。
- 旧用户无需重置密码即可迁移。
- 伪造其他用户 ID 无法访问其资源。

## 8. 阶段 3：协议 V2

### 8.1 编码规则

协议不再传输原始结构体。整数使用固定宽度类型和网络字节序；字符串使用 UTF-8 和显式长度；每种消息由独立编解码函数处理。

通用包头包含：魔数、协议版本、消息类型、请求 ID、标志位和正文长度。文件块消息额外包含 64 位总大小、64 位偏移和块长度。

### 8.2 单一协议库

客户端与服务端共享一份不依赖 Qt 或 Linux API 的纯 C++ 协议库。协议库负责边界检查、序列化、反序列化和错误返回，不包含业务逻辑。

### 8.3 迁移

客户端与服务端同步发布 V2。为支持发布回滚，服务端可在限定迁移窗口内识别 V1；V2 稳定并验证完毕后移除 V1，不长期维护双协议。

### 8.4 验收标准

- Windows 和 Linux 对相同消息生成一致字节序列。
- 截断、超长、未知类型和随机输入均不会越界或崩溃。
- 客户端和服务端不存在独立维护的业务协议结构体副本。

## 9. 阶段 4：性能优化

性能改动必须由基准数据驱动，且不得降低数据一致性。

### 9.1 网络与线程

- epoll 线程只维护连接和 I/O 状态。
- 数据库和磁盘任务交给有上限的工作队列。
- 全局发送锁改为每连接串行发送队列。
- 使用 `EPOLLOUT` 继续未完成发送，并对慢客户端实施背压。
- 线程池、文件任务和数据库连接池容量通过压测调节。

### 9.2 客户端

- 网络线程不直接操作 UI。
- 通过 Qt 信号传递状态，并限制进度刷新频率。
- 多任务调度设置并发上限，避免磁盘和网络竞争导致整体吞吐下降。

### 9.3 数据库

- 使用 `EXPLAIN` 验证登录、目录列表、MD5 秒传、分享码和文件关系查询。
- 避免循环内逐条 SQL，适合时使用批量查询或更新。
- 索引必须有查询证据，并评估写入成本。

### 9.4 基准指标

- 单文件和多文件吞吐量
- CPU、内存、磁盘和网络占用
- 登录及目录列表延迟
- 断线恢复耗时
- 慢客户端发送队列长度
- 传输后 MD5 和数据关系一致性

初始压力场景采用 50 个在线连接和 10 个并发大文件传输；该数量是开发基准，不代表生产容量承诺，后续按实际硬件与部署规模调整。

## 10. 阶段 5：模块重构与交付

### 10.1 客户端边界

- `AppController`：生命周期和组件组装
- `AuthService`：注册、登录和会话
- `FileService`：目录及文件操作
- `TransferManager`：上传、下载、暂停和续传
- `ShareService`：分享与提取
- `ProtocolCodec`：V2 编解码
- `NetworkClient`：TLS、收发和重连
- `TransferRepository`：SQLite 任务持久化

界面类只负责展示状态和接收用户操作，不直接访问网络、数据库或本地文件。

### 10.2 服务端边界

- `ServerConfig`
- `TcpTransport`
- `SessionManager`
- `AuthService`
- `FileService`
- `TransferService`
- `ShareService`
- `StorageService`
- `UserRepository` 与 `FileRepository`
- `ProtocolCodec`

业务服务不直接拼接 SQL 或物理路径，通过 Repository 和 Storage 接口访问外部资源。

### 10.3 构建与部署

- 稳定性阶段保留 qmake。
- 核心功能稳定后再单独评估迁移 CMake。
- 服务端提供 `systemd` 服务、独立运行用户、日志轮转和健康检查。
- 可执行文件、配置、日志、用户数据和数据库迁移脚本使用独立目录。
- 每个数据库版本提供向前升级脚本、执行前检查和回滚说明。

## 11. 测试策略

### 11.1 单元测试

覆盖协议编解码、路径校验、状态机、错误码、密码迁移和引用计数规则。

### 11.2 集成测试

使用测试 MySQL 和临时文件目录验证事务、上传提交、删除、秒传、分享及恢复逻辑。

### 11.3 端到端测试

真实客户端和服务端完成阶段 0 定义的全部冒烟流程，并检查数据库和物理文件结果。

### 11.4 故障与健壮性测试

覆盖断网、半包、非法包、磁盘满、数据库断开、进程重启、重复请求、并发请求和损坏文件。协议解码器增加模糊测试。

## 12. 数据迁移与回滚

- 所有迁移先在备份副本上演练。
- 数据库迁移使用单调递增版本号并记录执行结果。
- 不可逆迁移必须先保留原字段或备份表，经过稳定观察期后再清理。
- 密码迁移按用户逐步进行，不批量猜测或转换旧密码。
- 协议发布期间保留可回退的上一版客户端和服务端包。
- 回滚代码不得回滚已安全完成的用户数据，必要时通过兼容字段读取新旧格式。

## 13. 最终验收

- 原有账号、文件和分享关系完整保留。
- 核心功能、异常场景和数据恢复测试通过。
- 客户端与服务端协议只有一个权威定义。
- 源码、构建产物和日志中不存在真实密码或密钥。
- 上传下载完成后文件大小与 MD5 正确。
- 数据库关系、引用计数和物理文件保持一致。
- 压力测试期间内存保持稳定，不出现无限队列、明显死锁或跨用户数据泄漏。
- 干净环境能够根据文档完成构建、数据库升级、配置和部署。

## 14. 实施顺序约束

后续实施计划必须从阶段 0 开始，不允许跳过备份、基线和测试直接重构或优化性能。安全协议升级必须同时考虑旧密码迁移和发布回滚。任何性能改动必须附带相同环境下的前后基准与正确性验证。
