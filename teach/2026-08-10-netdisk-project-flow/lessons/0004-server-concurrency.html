Lesson 04 · 12 minutes

epoll、ONESHOT与线程池

目标：准确描述当前混合模型，并能解释它为什么不是“全非阻塞Reactor”。

LT epoll阻塞客户端socket生产者消费者

1. 网络事件路径

main → TcpKernel::Open
→ 连接MySQL
→ Block_Epoll_Net::InitNet
→ 创建监听socket并设为非阻塞
→ bind / listen / epoll_create
→ 注册EPOLLIN
→ EventLoop: epoll_wait
→ accept_event 或 recv_event

监听socket非阻塞；接受后的客户端socket设置缓冲区、TCP_NODELAY和30秒收发超时，但设置非阻塞的代码被注释。因此工作线程使用阻塞式 recvAllFd。

2. LT、ET和本项目

模式通知语义典型要求
LT只要仍就绪，就会继续通知可阻塞或非阻塞；更容易编写
ET状态变化时通知通常非阻塞并读到EAGAIN
本项目LT + EPOLLONESHOT工作线程阻塞读完整一帧

不要说“用了epoll，所以所有I/O都是非阻塞”。epoll只是就绪通知机制；具体socket是否阻塞由文件状态标志决定。

3. EPOLLONESHOT真正保证什么

一个客户端事件被取出后暂时失效，接收线程读完一帧后显式重新注册。这样可以避免两个线程同时从同一个socket读取字节流。

当前代码先把业务任务投递为 Buffer_Deal，随后立刻重新激活fd。所以下一个包可能在上一个业务尚未完成时被处理。ONESHOT保证“接收阶段不并发”，没有保证“同连接业务严格串行”。

4. 为什么还要线程池

epoll线程不应直接执行MySQL查询、递归目录或文件I/O，否则一个慢请求会阻塞整个事件循环。线程池通过环形队列实现生产者—消费者：

epoll发现可读 → 投递recv_task
recv_task读完整帧 → 投递Buffer_Deal
工作线程执行协议分发和业务

队列满：生产者等待not_full
队列空：消费者等待not_empty

管理线程每10秒采样存活、忙碌和排队数量，在10到200工作线程之间扩缩。

5. 并发安全的三个误区

  1. MyMap加锁不等于对象安全：find返回裸指针后立即解锁，其他线程可能删除对象。
  2. MySQL有锁不等于并行：单连接加递归锁保证调用安全，但所有SQL最终串行。
  3. 发送有锁不等于高性能：所有连接共享全局发送锁，慢连接可能阻塞其他连接。

6. 改进模型

  • 客户端socket非阻塞，每连接维护接收状态机。
  • 每连接一个串行strand/任务队列，业务完成后再消费下一包。
  • 传输map保存 shared_ptr<TransferContext>，明确生命周期。
  • 每连接独立发送队列，只在EPOLLOUT时继续短写。
  • MySQL连接池：一个任务/事务借用一个连接。

7. 面试口述

“服务端采用LT epoll监听就绪事件，监听socket非阻塞，但客户端socket当前是阻塞模式。EPOLLONESHOT避免同一fd被多个接收线程同时读取；工作线程先读取包长和完整包体，再把业务任务投递到动态线程池。这个模型实现简单，也把阻塞数据库和文件操作移出事件循环，但慢连接会占用工作线程，而且业务任务投递后立即重置ONESHOT，所以同一连接的业务仍可能并行。生产化会改为非阻塞连接状态机和连接级串行队列。”

8. 检索练习

问题：为什么条件变量等待必须用while而不是if？

条件变量允许虚假唤醒；多个消费者被唤醒时，前一个线程也可能已经取走任务。被唤醒后必须再次检查队列是否仍为空、线程池是否仍运行。
