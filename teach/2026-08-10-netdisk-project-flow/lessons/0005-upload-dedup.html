Lesson 05 · 12 minutes

上传状态机与内容去重

目标：能逐包复述普通上传与秒传分支，并解释ACK、f_state和引用计数分别解决什么问题。

64 KiB分块MD5秒传引用计数

1. 客户端准备

  1. 读取 QFileInfo：文件名、大小、路径。
  2. 同步遍历文件，计算MD5。
  3. 生成 hhmmsszzz任务时间戳，并在当前map中避碰。
  4. 以二进制方式打开源文件。
  5. 保存到 timestamp → FileInfo。
  6. 发送上传元数据请求。

整文件MD5在GUI线程执行，大文件会阻塞界面；文件大小使用32位int，不能可靠支持2 GiB以上文件。

2. 服务端三条分支

收到UPLOAD_FILE_RQ
├─ 参数/路径/MD5非法 → failed
├─ 同用户同目录同名 → name_exists
├─ MD5命中已完成文件 → 插入t_user_file → QUICK_UPLOAD_RS
└─ 未命中
   ├─ 创建物理临时文件
   ├─ 插入t_file(f_state=0, f_count=0)
   ├─ 插入t_user_file
   └─ 返回fileid → 开始传块

3. 普通上传的数据泵

客户端 fread
最多64 KiB
FILE_CONTENT_RQ
服务端 writeAll
FILE_CONTENT_RS
客户端更新pos
发送下一块

这是一种 stop-and-wait 应用层协议：同时最多只有一个未确认块。它自然形成背压，避免发送方无限堆积；但吞吐上限会受到RTT影响。

若块为64 KiB、往返时延50 ms，忽略其他开销，单任务上限约为 64 KiB / 0.05 s ≈ 1.25 MiB/s。优化方向是滑动窗口，而不只是增大块。

4. f_state、ACK、MD5别混为一谈

机制职责
f_state=0/1隔离上传中对象与可用对象；秒传只命中状态1
每块ACK确认该块被业务处理，推进发送状态机
MD5当前用于查重键；源码没有在服务端最终重新计算完整文件MD5
f_count记录物理对象被多少用户文件关系引用

不能说“服务端通过MD5保证完整性”。服务端相信客户端声明的MD5；如果客户端恶意或本地文件在计算后被修改，错误内容可能以该MD5入库并污染后续秒传。

5. 秒传的数据模型

t_file      = 物理对象：path / size / md5 / state / count
t_user_file = 逻辑文件：user / file / dir / name / time

同一t_file ← 用户A的关系
           ← 用户B的关系
           ← 用户A另一个目录的关系

新增关系由触发器增加引用数；删除关系减少引用数。只有引用降到0，才考虑删除物理对象。

6. 并发一致性追问

“先查重、再插入”存在TOCTOU：两个并发请求都可能查到不存在，然后都插入。因此数据库必须用 UNIQUE(u_id, f_dir, f_name)作为最终防线。当前优化脚本只把唯一索引留在注释中，不能假设部署环境已经建立。

7. 面试口述

“上传先发元数据，服务端检查同目录重名和MD5秒传。命中已完成物理文件时只新增用户文件关系；未命中则创建f_state=0的物理对象和关系，返回fileid。随后客户端每次发64 KiB，服务端完整写盘后ACK，客户端收到ACK才推进pos并发下一块，完成后服务端把f_state改为1。物理文件和用户逻辑文件分表，通过引用计数支持去重删除。当前MD5没有在服务端最终重算，所以只能说用于去重，不能声称完成了强完整性校验。”

8. 检索练习

问题：为什么秒传查询必须限定 f_state=1？为什么预查询不能替代唯一索引？

状态1保证被复用的是完整对象；状态0可能只有部分内容。预查询与插入不是一个原子动作，并发请求可同时通过检查；唯一索引由数据库在写入点保证最终唯一性。
