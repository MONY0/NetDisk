Lesson 07 · 12 minutes

谁的进度才可信

目标：讲清暂停、进程退出、重连和服务端重启后的恢复依据，并理解“记录进度”不等于“数据已持久化”。

SQLite检查点权威位置幂等恢复

1. 客户端持久化什么

登录后按userid创建独立SQLite文件，其中 t_upload 和 t_download保存：

timestamp / fileid / name / dir / time / size / md5 / type
absolutePath / pos / is_pause

进度不是每个64 KiB都写数据库，而是大约每256 KiB或完成时检查点，以减少频繁SQLite写入。

2. 上传恢复：服务端长度权威

客户端恢复任务并打开源文件
→ CONTINUE_UPLOAD_RQ
→ 服务端按user+fileid+dir查物理路径
→ 打开临时文件并lseek到末尾
→ 返回服务端实际pos
→ 客户端fseek到pos
→ 继续发块

不能信客户端自己报告的上传位置，因为它可能先更新本地记录、服务端却尚未落盘，也可能被篡改。

3. 下载恢复：客户端文件长度权威

客户端读取本地临时文件实际size
→ CONTINUE_DOWNLOAD_RQ(pos)
→ 服务端重建下载上下文
→ lseek源文件到pos
→ 继续发送下一块

SQLite可能落后于已写入磁盘的字节，因此恢复下载时以本地文件真实长度为准，而不是盲信SQLite中的pos。

4. 暂停和恢复的方向差异

方向数据驱动方恢复动作
上传客户端主动发下一块服务端返回pos，客户端重新启动发送
下载服务端主动发下一块服务端收到pos后重新启动读取发送

5. 仅比较长度还不够

长度相同不代表前缀内容相同。客户端源文件可能在暂停期间被修改，本地下载文件也可能被其他程序覆盖。可靠方案应保存分片摘要，恢复时校验最后一个已完成分片，最终再验证完整SHA-256。

6. timestamp不是可靠任务ID

当前timestamp来自 hhmmsszzz，不包含日期、设备和随机数。进程内碰撞会递增，但跨重启、多设备和同账号并发仍可能碰撞。服务端组合键 userid * 1e9 + timestamp只是把两个数拼起来，并没有创造真正全局唯一性。

更稳妥：由服务端生成UUID形式的 transfer_id，客户端SQLite、协议和服务端任务表统一使用。

7. 数据库与文件系统的一致性

事务可以保证多条MySQL语句原子提交，但不能把 write/unlink/rename自动加入同一事务。生产上传通常采用：

创建临时对象
→ 写分片并保存状态
→ 校验完整摘要
→ 数据库提交AVAILABLE
→ 原子rename/对象存储commit
→ 补偿任务处理异常中间态

8. 面试口述

“客户端按用户用SQLite保存传输元数据和检查点，但恢复时不完全相信数据库。上传以服务端临时文件长度为权威，因为只有服务端知道已经落盘多少；下载以客户端本地文件实际长度为权威，因为SQLite检查点可能落后。双方通过继续上传/下载协议重新建立文件句柄和偏移。当前只校验长度、任务ID也只是当天时间，生产化应使用服务端生成的transfer_id、分片摘要、最终哈希和异常状态补偿。”
